# 1. Общие принципы работы ИИ при программировании

ИИ при выполнении задач по разработке должен соблюдать следующие принципы:

1. Код должен быть рабочим, полным и запускаемым.
   - Нельзя выдавать фрагменты, которые невозможно использовать без скрытых догадок.
   - Если для запуска нужны зависимости, команды, конфигурация или переменные окружения — они должны быть явно указаны.

2. Запрещено выдумывать несуществующие API, библиотеки, методы, классы, модули или параметры.
   - Если точное поведение API неизвестно, ИИ обязан явно это указать.
   - Нельзя использовать псевдокод как финальное решение, если требуется реальный код.

3. Задача должна быть понята до начала реализации.
   - Если требование двойственное, неполное или противоречивое, ИИ должен либо уточнить детали, либо явно перечислить принятые допущения.
   - Не допускается самовольное изменение постановки задачи.

4. Результат должен быть проверяемым.
   - ИИ должен предоставлять способ проверки: тесты, примеры запуска, команды сборки, сценарии проверки, ожидаемое поведение.
   - Если выполнить проверку в текущей среде невозможно, ИИ должен явно сообщить об этом и предложить воспроизводимый способ проверки вручную.

5. Нельзя оставлять временные заглушки без явного согласования.
   - TODO, FIXME, pass, ..., NotImplementedException, пустые функции и классы не допускаются в финальном решении, если они не являются частью согласованного интерфейса или отдельного этапа работы.


# 2. Обязательная формализация задачи перед написанием кода

Перед созданием кода ИИ должен определить или запросить следующие сведения:

1. Язык программирования и версия языка.
   Например:
   - Python 3.11+
   - C# 12 / .NET 8
   - JavaScript ES2022 / Node.js 20
   - TypeScript 5.x
   - HTML5 / CSS3

2. Платформа и окружение.
   Например:
   - консольное приложение;
   - веб-приложение;
   - браузер;
   - сервер;
   - Docker;
   - конкретный фреймворк: ASP.NET Core, FastAPI, Django, React, Vue и т.д.

3. Назначение программы или модуля.
   - Что именно должно быть реализовано.
   - Какие входные данные принимаются.
   - Какие выходные данные ожидаются.
   - Какие ограничения существуют.

4. Критерии готовности.
   - Что считается корректным результатом.
   - Какие случаи должны обрабатываться.
   - Какие ошибки должны перехватываться.
   - Нужны ли тесты, документация, конфигурация.

5. Список зависимостей.
   - Какие библиотеки разрешено использовать.
   - Какие версии библиотек требуются.
   - Можно ли добавлять новые зависимости.

6. Требования к безопасности и качеству.
   - Валидация ввода.
   - Обработка ошибок.
   - Логирование.
   - Защита от типовых уязвимостей.
   - Производительность.
   - Масштабируемость.

Если часть данных неизвестна, ИИ должен:
- либо задать минимально необходимые уточняющие вопросы;
- либо явно зафиксировать допущения, например:

«Если формат входных данных не указан, считается, что входом является строка в кодировке UTF-8 (за исключением текстовых файлов, которые для русского языка лучше рассматривать в кодировке windows 1251)»


# 3. Запрещённые паттерны и типовые дефекты

При создании кода запрещается:

## 3.1. Синтаксические ошибки

Запрещено выдавать код с:
- незакрытыми скобками;
- незакрытыми строками;
- неверными отступами в Python;
- отсутствующими точками с запятой там, где они обязательны;
- неверным синтаксисом объявлений;
- ошибками в ключевых словах;
- некорректными конструкциями языка.

Код должен проходить базовую проверку синтаксиса, если такая проверка доступна.

## 3.2. Пустые объявления

Запрещены пустые объявления без функциональной необходимости:

```python
def process_data():
    pass
```

```csharp
public void Save()
{
}
```

```javascript
function submitForm() {
}
```

Пустые объявления допустимы только если:
- это абстрактный метод;
- это интерфейс;
- это явная заготовка, согласованная с пользователем;
- это часть архитектурного каркаса, и пользователь явно это разрешил.

Во всех остальных случаях функция, метод или класс должны содержать реальную реализацию.

## 3.3. Заглушки

Запрещено использовать заглушки в финальном коде:

```python
def calculate_total():
    # TODO: implement
    return 0
```

```csharp
public string GetData()
{
    throw new NotImplementedException();
}
```

```javascript
async function fetchUser() {
    // TODO
    return null;
}
```

Исключение:
- пользователь явно запросил заглушку;
- заглушка является частью этапа проектирования;
- внешняя система недоступна, и это явно указано в ограничениях.

## 3.4. Неправильный импорт

Запрещено:
- импортировать несуществующие модули;
- использовать неправильные относительные пути;
- забывать установить зависимости;
- путать имена пакетов и имена импортируемых модулей;
- использовать устаревшие или удалённые модули;
- создавать циклические импорты без необходимости;
- применять импорт, который не используется.

Пример недопустимого:

```python
from utils.helpers import parse_json
```

если файла `utils/helpers.py` или функции `parse_json` не существует.

Для каждого импорта должно быть понятно:
- откуда берётся модуль;
- является ли он стандартной библиотекой;
- является ли он внешней зависимостью;
- как установить внешнюю зависимость;
- какая версия требуется.

## 3.5. Необъявленные переменные и неопределённые значения

Запрещено использовать переменные, функции или классы, которые не были объявлены ранее или не импортированы.

Недопустимо:

```python
result = calculate(data)
```

если функция `calculate` не определена и не импортирована.

В JavaScript недопустимо:

```javascript
console.log(userName);
let userName = "Ivan";
```

если ожидается использование до объявления без явной необходимости.

## 3.6. Неинициализированные переменные

Переменные должны быть инициализированы до использования, если это требуется языком и логикой.

Недопустимо оставлять переменные без значения, если дальнейшая логика от них зависит.

## 3.7. Мёртвый код

Запрещено оставлять:
- неиспользуемые функции;
- неиспользуемые переменные;
- закомментированные блоки без пояснения;
- недостижимый код;
- неиспользуемые импорты;
- отладочный вывод без необходимости.

## 3.8. Неполная обработка ошибок

Запрещено игнорировать ошибки без явной причины.

Недопустимо:

```python
try:
    do_something()
except:
    pass
```

Если ошибка перехватывается, должно быть понятно:
- какое исключение перехватывается;
- почему оно может возникнуть;
- что происходит после перехвата;
- логируется ли ошибка;
- возвращается ли пользователю понятный результат.

## 3.9. Небезопасная работа с пользовательским вводом

Запрещено:
- выполнять произвольный код из пользовательского ввода;
- использовать небезопасную десериализацию;
- подставлять пользовательские данные в SQL-запросы без параметризации;
- вставлять пользовательский ввод в HTML без экранирования;
- использовать пользовательский ввод в командах ОС без санитизации.

## 3.10. Хардкод секретов

Запрещено вшивать в код:
- пароли;
- токены;
- API-ключи;
- приватные ключи;
- строки подключения с паролями;
- персональные данные, если это не тестовые синтетические данные.

Секреты должны передаваться через:
- переменные окружения;
- секреты платформы;
- конфигурационные хранилища;
- менеджер секретов.


# 4. Требования к качеству кода

ИИ должен создавать код, соответствующий следующим требованиям.

## 4.1. Читаемость

- Имена переменных, функций, классов и модулей должны быть понятными.
- Именование должно отражать назначение сущности.
- Следует избегать однобуквенных переменных, кроме очевидных случаев: индексы циклов, математические обозначения.
- Код должен быть структурирован и не перегружен вложенностью.

Плохо:

```python
def f(x):
    if x:
        return x * 2
    return 0
```

Лучше:

```python
def double_positive_number(value: int) -> int:
    if value > 0:
        return value * 2
    return 0
```

## 4.2. Единый стиль

Код должен быть оформлен единообразно:
- единый стиль отступов;
- единый стиль кавычек, если это уместно;
- единый стиль именования;
- единый порядок импортов;
- отсутствие смешанных стилей без необходимости.

Рекомендуется использовать форматтер, если он доступен:
- `black`, `ruff format` для Python;
- `dotnet format` для C#;
- `prettier` для JavaScript/TypeScript/HTML/CSS;
- `eslint` для JavaScript/TypeScript.

## 4.3. Типизация и контракт данных

Если язык поддерживает типизацию, следует использовать её явно.

Для Python желательно указывать типы аргументов и возвращаемых значений:

```python
def calculate_average(values: list[float]) -> float:
    ...
```

Для TypeScript следует избегать неявного `any`:

```typescript
function sum(a: number, b: number): number {
    return a + b;
}
```

Для C# следует использовать явные типы там, где это улучшает читаемость и безопасность:

```csharp
public int CalculateSum(IReadOnlyList<int> values)
{
    ...
}
```

## 4.4. Валидация входных данных

Все внешние данные должны проверяться:
- аргументы функций;
- данные из сети;
- данные из файлов;
- данные из переменных окружения;
- пользовательский ввод;
- данные из базы данных, если они могут быть некорректными.

Необходимо проверять:
- наличие обязательных полей;
- типы данных;
- диапазоны значений;
- пустые значения;
- формат строк;
- размер данных;
- допустимые перечисления.

## 4.5. Обработка ошибок

Код должен корректно обрабатывать ожидаемые ошибки:
- файл не найден;
- сетевой запрос не выполнен;
- сервер вернул ошибку;
- пришли некорректные данные;
- отсутствует переменная окружения;
- база данных недоступна;
- пользователь ввёл неверные данные.

Обработка ошибок должна быть осмысленной:
- логирование;
- возврат понятного результата;
- проброс исключения с контекстом;
- повторная попытка, если это допустимо;
- аварийное завершение с понятным сообщением, если продолжение невозможно.

## 4.6. Логирование

Если задача предполагает диагностику, код должен содержать логирование:
- входных параметров без секретов;
- ключевых этапов выполнения;
- ошибок;
- исключений;
- результата операции.

Запрещено логировать:
- пароли;
- токены;
- ключи;
- персональные данные без необходимости;
- содержимое секретных документов.

## 4.7. Идемпотентность и повторный запуск

Если код выполняет операции с побочными эффектами, следует учитывать повторный запуск:
- запись в файл;
- отправка запроса;
- создание записи в базе данных;
- выполнение миграции;
- создание файлов или директорий;
- запуск фоновых задач.

Там, где возможно, операции должны быть идемпотентными или защищёнными от дублирования.

## 4.8. Работа с ресурсами

Все ресурсы должны корректно освобождаться:
- файлы;
- сетевые соединения;
- потоки;
- таймеры;
- соединения с базой данных;
- временные файлы.

В разных языках это реализуется через:
- `with` в Python;
- `using` в C#;
- `try/finally`;
- `AbortController`, `clearInterval`, `clearTimeout` в JavaScript;
- закрытие соединений и потоков.

## 4.9. Производительность

Код должен быть разумно эффективным.

Запрещено без необходимости:
- использовать квадратичные алгоритмы для больших данных;
- многократно читать один и тот же файл;
- делать запросы в цикле без батчинга;
- создавать избыточные копии больших данных;
- блокировать поток ввода-вывода без необходимости;
- выполнять синхронные операции там, где требуется асинхронность.

Если ожидается большой объём данных, следует учитывать:
- потоковую обработку;
- пагинацию;
- батчинг;
- кэширование;
- индексы;
- лимиты памяти и времени.


# 5. Требования к зависимостям

ИИ должен соблюдать правила работы с внешними библиотеками.

1. Использовать только реально существующие пакеты.
   Запрещено выдумывать названия пакетов, модулей и функций.

2. Указывать способ установки.
   Например:

   ```bash
   pip install requests
   ```

   ```bash
   dotnet add package Newtonsoft.Json
   ```

   ```bash
   npm install axios
   ```

3. Учитывать версии.
   Если код зависит от версии библиотеки, версия должна быть указана.

4. Не добавлять лишние зависимости.
   Если задачу можно решить стандартной библиотекой, не следует без необходимости тянуть тяжёлый пакет.

5. Проверять лицензионную и правовую уместность.
   Если пользователь указал ограничения по лицензиям, их нужно соблюдать.

6. Разделять runtime-зависимости и dev-зависимости.
   Инструменты тестирования, линтеры и форматтеры не должны выдаваться за зависимости, необходимые для работы приложения, если это не требуется.

7. Проверять совместимость.
   Библиотека должна соответствовать:
   - версии языка;
   - платформе;
   - окружению;
   - целевой ОС;
   - браузеру или серверу;
   - архитектуре проекта.


# 6. Требования к тестированию

Если задача требует надёжности, ИИ должен добавить тесты или как минимум сценарии проверки.

## 6.1. Обязательные категории тестов

Необходимо проверять:

1. Позитивные сценарии.
   Программа работает с корректными входными данными.

2. Негативные сценарии.
   Программа не падает неконтролируемо при некорректных данных.

3. Граничные случаи.
   - пустой ввод;
   - один элемент;
   - максимальный размер;
   - нулевые значения;
   - отрицательные значения;
   - очень длинные строки;
   - специальные символы;
   - Unicode;
   - null / None / undefined;
   - отсутствие поля;
   - неверный тип данных.

4. Ошибки окружения.
   - нет файла;
   - нет сети;
   - нет переменной окружения;
   - нет доступа к базе данных;
   - недостаточно прав;
   - таймаут.

5. Повторное использование.
   - повторный вызов функции;
   - повторный запуск скрипта;
   - повторная отправка формы;
   - повторная запись в файл.

## 6.2. Требования к тестам

Тесты должны:
- быть автоматическими, если это возможно;
- иметь понятные имена;
- проверять конкретное поведение;
- не зависеть от порядка выполнения;
- не требовать ручных действий без необходимости;
- очищать создаваемые ресурсы;
- использовать фикстуры или моки только там, где это уместно.

Запрещено:
- писать тесты без утверждений;
- тестировать только один идеальный сценарий;
- оставлять тесты, которые всегда проходят независимо от кода;
- маскировать ошибку вместо её проверки;
- использовать моки там, где можно проверить реальное поведение.

## 6.3. Минимальный набор проверок

Если полноценный тестовый фреймворк не требуется, ИИ должен предоставить хотя бы:
- пример входных данных;
- команду запуска;
- ожидаемый результат;
- поведение при ошибке;
- список ручных проверок.


# 7. Требования к импорту и структуре проекта

ИИ должен проверять структуру проекта и корректность импортов.

## 7.1. Проверка путей импорта

Необходимо убедиться, что:
- файл существует;
- модуль доступен;
- путь импорта корректен;
- пакет имеет `__init__.py`, если это требуется;
- относительные импорты допустимы;
- имя файла не конфликтует со стандартной библиотекой;
- нет циклических зависимостей.

## 7.2. Разделение ответственности

Код следует разделять на логические модули:
- модели;
- сервисы;
- репозитории;
- обработчики;
- утилиты;
- конфигурация;
- точки входа;
- тесты.

Не следует помещать всю логику в один файл без необходимости, если это ухудшает читаемость и поддержку.

## 7.3. Точка входа

Если программа запускаемая, должна быть понятная точка входа.

Для Python:

```python
if __name__ == "__main__":
    main()
```

Для C#:

```csharp
public static class Program
{
    public static void Main(string[] args)
    {
        // запуск приложения
    }
}
```

Для JavaScript:

```javascript
main();
```

или экспорт модуля, если это библиотека.


# 8. Требования к пользовательскому интерфейсу

Если задача связана с HTML, CSS или JavaScript-интерфейсом, код должен быть не только синтаксически корректным, но и рабочим визуально и функционально.

## 8.1. Интерактивность

Если заявлено, что интерфейс работает:
- кнопки должны обрабатывать клики;
- формы должны отправляться или перехватываться;
- поля должны валидироваться;
- модальные окна должны открываться и закрываться;
- списки должны обновляться;
- ошибки должны отображаться пользователю;
- загрузка должна иметь визуальное состояние;
- элементы не должны ломать разметку.

## 8.2. Доступность

По возможности следует соблюдать базовую доступность:
- `label` для полей ввода;
- осмысленные `alt`;
- контрастность;
- управление с клавиатуры;
- семантические теги;
- понятные сообщения об ошибках.

## 8.3. Безопасность фронтенда

Запрещено:
- вставлять пользовательский ввод в `innerHTML` без экранирования;
- выполнять произвольный код через `eval`;
- хранить чувствительные токены в `localStorage`, если это не обосновано и не согласовано;
- отправлять чувствительные данные без HTTPS;
- доверять данным, пришедшим из браузера.


# 9. Требования к работе с данными и базами данных

Если код работает с данными, необходимо учитывать следующее.

## 9.1. Целостность данных

- Данные не должны теряться при ошибке, если это не ожидаемое поведение.
- Использовать транзакции там, где операция должна быть атомарной.
- Проверять ограничения: уникальность, обязательность, внешние ключи.
- Не полагаться только на проверку в интерфейсе.

## 9.2. Безопасность запросов

- Использовать параметризованные запросы.
- Не конкатенировать пользовательский ввод в SQL.
- Избегать сырых запросов без необходимости.
- Проверять права доступа к данным.

## 9.3. Производительность

- Избегать N+1 запросов.
- Использовать пагинацию для больших выборок.
- Добавлять индексы там, где это обосновано.
- Не выбирать лишние поля без необходимости.

## 9.4. Миграции

Если код меняет схему данных:
- миграция должна быть воспроизводимой;
- должна учитывать откат или ограничения отката;
- должна быть безопасной для существующих данных;
- должна быть протестирована на копии данных.


# 10. Требования к безопасности

ИИ должен учитывать базовые риски безопасности.

## 10.1. Типовые уязвимости

Необходимо проверять код на риски:
- SQL-инъекции;
- XSS;
- CSRF;
- небезопасная десериализация;
- выполнение произвольных команд;
- чтение произвольных файлов;
- запись в произвольные файлы;
- раскрытие секретов;
- избыточные права доступа;
- небезопасные зависимости;
- утечка данных в логах.

## 10.2. Принцип минимальных привилегий

Код должен запрашивать только необходимые права:
- доступ только к нужным файлам;
- доступ только к нужным сетевым адресам;
- минимальные разрешения для базы данных;
- минимальные права ОС;
- минимальные области видимости токенов.

## 10.3. Защита данных

- Не хранить пароли в открытом виде.
- Использовать современные алгоритмы хэширования паролей, например `bcrypt`, `Argon2`, `PBKDF2`, если задача требует аутентификации.
- Не передавать чувствительные данные в открытом виде.
- Валидировать и экранировать пользовательский ввод.
- Не показывать пользователю внутренние детали ошибок, если это небезопасно.


# 11. Требования к документации и комментариям

Документация должна быть полезной и не дублировать очевидное.

## 11.1. Что нужно документировать

- назначение модуля;
- как запустить проект;
- как установить зависимости;
- как настроить переменные окружения;
- как использовать ключевые функции;
- какие ошибки возможны;
- как проверить результат;
- известные ограничения.

## 11.2. Комментарии

Комментарии нужны для объяснения:
- неочевидной бизнес-логики;
- обходных решений;
- причин выбора алгоритма;
- особенностей совместимости;
- временных ограничений.

Не нужно комментировать тривиальный код без пользы.


# 12. Обязательная самопроверка перед выдачей результата

Перед тем как выдавать код, ИИ должен выполнить самопроверку по следующему списку.

## 12.1. Проверка синтаксиса

- Код компилируется или интерпретируется без синтаксических ошибок.
- Нет незакрытых скобок, строк, блоков.
- Отступы корректны.
- Ключевые слова написаны правильно.
- Конструкции языка используются корректно.

## 12.2. Проверка импортов

- Все импорты существуют.
- Все зависимости указаны.
- Пути импорта корректны.
- Нет неиспользуемых импортов.
- Нет циклических импортов.
- Нет конфликта имён.

## 12.3. Проверка объявлений

- Все функции, классы и переменные объявлены до использования.
- Нет пустых функций без причины.
- Нет заглушек вместо реализации.
- Нет TODO/FIXME в финальном коде без согласования.

## 12.4. Проверка логики

- Код решает именно поставленную задачу.
- Учтены входные и выходные данные.
- Учтены граничные случаи.
- Нет мёртвого кода.
- Нет лишних действий.
- Нет логических противоречий.
- Нет неверных условий.
- Нет недостижимых веток.

## 12.5. Проверка ошибок

- Ошибки обрабатываются.
- Исключения не проглатываются молча.
- Пользователь или вызывающий код получает понятный результат.
- Ошибки логируются, если это уместно.

## 12.6. Проверка безопасности

- Нет секретов в коде.
- Пользовательский ввод проверяется.
- Нет опасных вызовов.
- SQL-запросы параметризованы.
- HTML экранируется при необходимости.
- Файловые пути проверяются.

## 12.7. Проверка запуска

Если доступна среда исполнения:
- код запускается;
- основной сценарий работает;
- ошибки воспроизводятся и обрабатываются;
- тесты проходят;
- линтер не выдаёт критических ошибок;
- форматирование корректно.

Если среда исполнения недоступна:
- ИИ явно сообщает об этом;
- предоставляет инструкцию по запуску;
- предоставляет ожидаемый результат;
- предоставляет проверочные примеры.


# 13. Критерии готовности результата

Результат считается готовым только если выполнены все пункты:

1. Код написан на корректном языке и версии.
2. Код решает поставленную задачу.
3. Нет синтаксических ошибок.
4. Нет пустых объявлений без необходимости.
5. Нет заглушек вместо реализации.
6. Нет неиспользуемых переменных и функций.
7. Все импорты корректны.
8. Все зависимости указаны.
9. Внешние данные валидируются.
10. Ошибки обрабатываются.
11. Секреты не хранятся в коде.
12. Есть инструкция по установке и запуску.
13. Есть примеры использования.
14. Есть тесты или сценарии проверки.
15. Поведение при некорректных данных определено.
16. Код не содержит небезопасных конструкций без обоснования.
17. Все допущения явно указаны.
18. Известные ограничения описаны.


# 14. Языково-специфичные проверки

## 14.1. Python

Обязательно проверять:
- корректность отступов;
- наличие всех импортов;
- отсутствие конфликта имён модулей со стандартной библиотекой;
- типы аргументов и возвращаемых значений при необходимости;
- использование `with` для файлов;
- обработку `None`;
- проверку исключений;
- кодировку файлов;
- корректность виртуального окружения;
- отсутствие `pip install` в коде без необходимости;
- корректность `requirements.txt` или `pyproject.toml`.

Примеры команд проверки:

```bash
python -m compileall .
ruff check .
mypy .
pytest
```

## 14.2. C# / .NET

Обязательно проверять:
- наличие всех `using`;
- корректность пространств имён;
- совместимость версии C# и .NET;
- отсутствие неиспользуемых переменных;
- корректность асинхронных методов;
- использование `using` для `IDisposable`;
- обработку исключений;
- отсутствие `async void` без крайней необходимости;
- корректность DI-регистраций;
- наличие тестов при необходимости.

Примеры команд проверки:

```bash
dotnet build
dotnet test
dotnet format --verify-no-changes
```

## 14.3. JavaScript / TypeScript

Обязательно проверять:
- корректность модульной системы: CommonJS или ESM;
- наличие всех импортов;
- отсутствие необъявленных переменных;
- корректность асинхронного кода;
- обработку `Promise` и `await`;
- отсутствие неперехваченных ошибок;
- корректность работы с DOM;
- очистку таймеров и подписок;
- валидацию пользовательского ввода;
- экранирование HTML.

Для TypeScript дополнительно:
- избегать `any` без необходимости;
- проверять типы;
- использовать строгий режим;
- проверять `strictNullChecks`.

Примеры команд проверки:

```bash
node --check file.js
npm run lint
npm run test
tsc --noEmit
```

## 14.4. HTML / CSS

Обязательно проверять:
- валидность разметки;
- закрытие тегов;
- корректность атрибутов;
- семантичность;
- наличие `alt` у изображений;
- связь `label` и `input`;
- корректность селекторов CSS;
- адаптивность;
- отсутствие конфликтующих стилей;
- доступность базового интерфейса.
